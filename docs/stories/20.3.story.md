# Story 20.3: Backend Subscription Logic & Payment Segregation

-   **Epic:** 20 (Tiffin Service Subscription Engine)
-   **Status:** Done

---

### User Story:
As a Developer, I need to enhance the backend to handle a new `SubscriptionOrder` type, correctly split multi-provider payments, and manage the subscription lifecycle.

---

### Acceptance Criteria:

1.  A new `SubscriptionOrder` interface is created to represent recurring orders, distinct from standard one-time `Order`s.
2.  The backend mock database (`api/mock.ts`) includes a new table to store `subscriptionOrders`.
3.  The main checkout API endpoint (`/api/orders/checkout`) is enhanced to differentiate between `MEAL` and `PLAN` items in the cart.
4.  When processing a cart, the checkout logic correctly creates standard `Order` objects for all `MEAL` items.
5.  When processing a cart, the checkout logic correctly creates new `SubscriptionOrder` objects for all `PLAN` items.
6.  The `checkout` API response is updated to return both the newly created orders and the newly created subscriptions.
7.  The system correctly calculates the `startDate` and `endDate` for new subscriptions based on the plan's duration.

---

### Technical Specification:

-   **Data Model (`types.ts`):**
    -   A new `SubscriptionOrder` interface has been created. It includes fields for `planId`, `planName`, `duration`, `startDate`, `endDate`, and a `status` of `'ACTIVE' | 'PAUSED' | 'COMPLETED' | 'CANCELLED'`.

-   **API Layer (`api/orderApi.ts`):**
    -   The return type of the `checkout` function has been updated from `Promise<{ createdOrders: Order[] }>` to `Promise<{ createdOrders: Order[]; createdSubscriptions: SubscriptionOrder[] }>`.

-   **Mock API (`api/mock.ts`):**
    -   The mock database object `db` now includes a new empty array: `subscriptionOrders: [] as SubscriptionOrder[]`.
    -   The handler for `POST /api/orders/checkout` has been significantly refactored.
    -   Inside its main loop that processes items by provider, it now filters the items into two groups: `mealItems` and `planItems`.
    -   The existing logic for creating a standard `Order` is now applied only to the `mealItems` group.
    -   A new block of logic iterates over the `planItems`. For each plan, it creates a new `SubscriptionOrder` object, calculates the `startDate` and `endDate`, and pushes it into the `db.subscriptionOrders` array.
    -   The final JSON response from the handler is updated to include both `createdOrders` and `createdSubscriptions`.
